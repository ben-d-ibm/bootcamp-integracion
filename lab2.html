⚙️ Creación de Workflow en IWHI

1

Crear el Workflow

Ve a Integrations → Workflows dentro de tu proyecto en IBM webMethods Integration. Si aún no tenés ningún workflow, verás la pantalla vacía con el botón +.

Hacé clic en el botón + y seleccioná Create New Workflow.

Se abrirá el canvas del workflow con el panel de conectores a la derecha y el bloque Define trigger vacío.

1.1 — Configurar el Trigger Webhook

Hacé clic en el bloque Define trigger. En el catálogo de triggers, seleccioná Webhook.

Payload de muestra (Mock Data): copiá la URL temporal que se genera y guardala. Luego ingresá el siguiente JSON en el campo Body:

{
  "numero_cuenta": "ES0100010001001234567890",
  "monto": 1000,
  "trx_id": 1234
}
CampoTipoDescripción
numero_cuentastringNúmero de cuenta del cliente emisor
montonumberMonto monetario de la transacción
trx_idnumberIdentificador único de la transacción

Una vez ingresado, hacé clic en Next.

Opciones del Webhook:

  • Private webhook: Off
  • Webhook Authentication: None
  • Autoconnect Return Sync on Webhook: Off — luego agregamos los bloques de Return explícitamente en cada rama.

Hacé clic en Next.

Aparecerá el mensaje "Webhook configured successfully!". Hacé clic en Done.

2

Agregar y Configurar el FlowService getClientInfo

2.1 — Buscar el conector FlowService

En el panel lateral de conectores, escribí getClientInfo en la barra de búsqueda.

Arrastrá el conector getClientInfo hacia el canvas justo después del bloque Webhook.

2.2 — Configurar el Runtime on-premise

En la ventana de configuración del bloque getClientInfo:

  1. Desplegá el selector Runtime.
  2. Seleccioná tu runtime (ej: beetech_runtime).
  3. Hacé clic en Next.

2.3 — Mapeo de parámetros de entrada

En Action configure, mapeá numero_cuenta proveniente de $request.body hacia el parámetro numero_de_cuenta del getClientInfo.

💡 Tip: Para seleccionar un Incoming Data, hacé click primero en la casilla que querés completar en Active Configure y luego seleccioná el dato (numero_cuenta de $request.body). Se asignará automáticamente.

Hacé clic en Next.

2.4 — Probar la ejecución de la acción

webMethods Integration ejecutará una prueba unitaria usando el payload de muestra para validar la conectividad. Hacé clic en Test.

Verificá que la prueba retorne "Message posted successfully" y que los campos del cliente se reciban correctamente. Hacé clic en Done.

3

Agregar el Bloque de Decisión (Switch)

En el panel lateral, buscá switch. En la sección Developer Tools, seleccioná el conector Switch.

Arrastrá el bloque Switch al canvas y conectalo a la salida de getClientInfo.

4

Agregar los Bloques de Respuesta (Return Data on Sync Webhook)

Para devolver una respuesta HTTP al cliente según el resultado de la evaluación, usaremos el bloque Return Data on Sync Webhook.

4.1 — Buscar el bloque

En el panel lateral, buscá el bloque por su nombre. Seleccioná Return Data on Sync Webhook bajo Developer Tools.

4.2 — Conectar el primer bloque de retorno (Rama 1)

Arrastrá el primer bloque Return Data on Sync Webhook conectándolo a la primera rama del Switch.

4.3 — Conectar el segundo bloque de retorno (Rama 2)

Arrastrá un segundo bloque Return Data on Sync Webhook conectándolo a la segunda rama del Switch. Esta comenzará llamándose Case 2; en el Paso 5.2 se definirá como Default.

5

Configurar las Condiciones del Switch

Configuraremos las reglas lógicas que determinarán qué rama toma el flujo:

  • Case 1 (Aprobado): el monto es menor o igual al saldo disponible (monto ≤ saldo_1).
  • Default (Rechazado): el monto excede el saldo disponible.

5.1 — Configurar Case 1 (Condición de Aprobación)

Hacé clic en la primera rama del Switch. Saldrán 4 íconos disponibles. Hacé clic sobre el engranaje de configuración.

En el editor de condiciones:

  1. En Select Case, asegurate de estar en Case 1.
  2. En Condition Activity, seleccioná Add Condition → Add Filter.
  3. En Filter 1, en Input seleccioná $request → body → monto.
  4. En Condition seleccioná (Number) Less Than Equals.

En Expected, seleccioná el campo de saldo del FlowService: $a0 - getClientInfo → results → saldo_1. Hacé clic en Done.

5.2 — Configurar Caso Default (Condición de Rechazo)

Hacé clic en la configuración de la segunda rama del Switch.

Seleccioná Case 2 y elegí la opción Default. Al ser la condición complementaria, no requiere filtros adicionales. Hacé clic en Done.

Configurar los Bloques de Respuesta

6.1 — Configurar "Caso Aprobación"

Abrí el bloque de respuesta de la primera rama y renombralo a Caso Aprobación.

Response Data:

{"resultado": "aprobado", "trx_id": {{$request.body.trx_id}}, "numero_cuenta": "{{$request.body.numero_cuenta}}", "monto": {{$request.body.monto}}, "nombre": "{{$a0.results[0].nombre_1}}", "apellido": "{{$a0.results[0].apellido_1}}", "saldo": {{$a0.results[0].saldo_1}}}

Hacé clic en Next.

9

Probar con el Transaction Tester

9.1 — Levantar el contenedor

Asegurate de tener corriendo la base de datos (iniciada en el Lab 1) y levantá el servicio desde la raíz del proyecto:

Docker

docker compose up -d transaction-tester

Podman

podman compose up -d transaction-tester

Abrí http://localhost:8080 en el navegador.

9.2 — Configurar la URL del webhook

  1. Pegá la URL del webhook copiada en el campo URL del workflow (IWHI).
  2. Hacé clic en Cargar cuentas para recuperar la lista de clientes desde la base de datos.

9.3 — Ejecutar transacciones y validar resultados

  1. Seleccioná un cliente (ej: Carlos Ramírez Vega, saldo $3,200).
  2. Prueba de Aprobación: ingresá un monto inferior al saldo → HTTP 200 con "resultado": "aprobado".
  3. Prueba de Rechazo: ingresá un monto mayor al saldo → HTTP 200 con "resultado": "rechazado" y "motivo": "Saldo insuficiente".
